# Claude 产品线、Claude Code 与 Cowork

核对日期：2026-10-17。产品形态正在变化，先看当前官方说明，再理解各部分解决的问题。

## 一、先画产品结构

| 部分 | 使用者的主要目标 | 组织单位 |
| --- | --- | --- |
| Claude 模型与 API | 把推理、多模态和工具能力接入自己的应用 | 请求、上下文、工具结果 |
| Claude 对话 | 讨论、理解、写作、分析 | 对话 |
| Projects | 围绕一个主题组织资料与指导 | 项目材料与任务 |
| Artifacts | 制作、查看、编辑和分享成果 | 文档、演示、设计、交互工具等对象 |
| Claude/Cowork 的任务执行 | 交给系统一项多步骤知识工作 | 任务、工具操作和完成文件 |
| Claude Code | 推进工程任务，并接入开发环境 | 代码、命令、会话和变更 |
| Skills、Connectors、Plugins | 复用流程并引入外部系统 | 专用流程与工具连接 |

这是按用户任务整理的地图，不是互斥的官方套餐清单。当前官方已说明，Cowork 正逐步与 Claude 聊天合并，同一段对话可以处理快速问答和较长任务。[统一体验](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude)

## 二、模型与 API：能力层怎样服务产品

官方模型页区分面向高强度推理、长任务、速度与成本等不同需求的系列。当前页列有 Fable、Opus、Sonnet、Haiku；具体版本、价格与平台支持应查模型页。[模型概览](https://platform.claude.com/docs/en/models/overview)

**产品判断：**不要只按“最强模型”选型。应使用真实任务检查成功率、延迟、调用成本和人工复核负担。一个便宜模型反复失败，整体可能更贵；一个能力很强的模型也未必适合低延迟交互。

API 给开发者的是能力和接口。用户登录、业务授权、数据更新、失败恢复和最终交互仍需要产品定义。消费端 Claude 的体验也不能直接推断为相同模型 API 的默认体验。

## 三、Claude 对话与 Projects

### 3.1 核心用户任务

用户往往带着尚未完全成形的问题进入：理解资料、找出思路、拟稿、比较方案。价值既来自结果，也来自用户能否在对话中不断纠正方向。

**产品判断：**写作协作需要保存用户判断，而不只是保存产生过的文字。用户说“这个人物不会这样讲话”，应改变后续创作依据。

### 3.2 Projects 解决资料组织

Projects 可保存项目资料和项目指导。官方说明也提醒，不应把同项目下的聊天理解成自动共享全部上下文；需要共享的内容应放进相应知识材料。[项目说明](https://support.claude.com/en/articles/9519177-how-can-i-create-and-manage-projects)

**设计问题：**资料多了以后，用户怎样知道这次回答用了什么、漏了什么、是否引用旧稿？“能上传更多资料”与“能用对资料”需要分别验证。

**适合你的做法：**把已经确认的人物设定、已废弃情节和当前故事问题整理成短文档。不要期待仅凭很多轮对话就能稳定区分它们。

## 四、Artifacts：从回答到可操作成果

官方将 Artifacts 作为对话旁可编辑、可返回和可分享的成果；当前包含 Docs、Slides、Design 等模板和其他交互成果，具体开放范围按账号及官方更新查看。[Artifacts](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them)

### 4.1 核心流程

提出成果要求 → 创建对象 → 在预览中检查 → 自己编辑或用自然语言修改 → 分享或导出。

### 4.2 产品价值

- 用户不必在长对话里反复复制完整内容。
- 修改可以围绕一个持续存在的对象进行。
- 阅读、操作和反馈更接近最终使用环境。

### 4.3 需要区分的三件事

1. 展示一个可以点击的界面。
2. 实现正确的业务逻辑和持久化状态。
3. 将系统部署给真实用户，并维护权限和数据。

第一件成立，不自动证明后两件。你的轮椅 Demo 需要验证选择影响下一次行为，就是从“有界面”走向“逻辑可体验”的例子。

### 4.4 可提出的产品问题

用户是在修改文案、修改设计，还是修改运行逻辑？如果同一个自然语言入口都接受，系统怎样帮助用户确认修改范围并验证结果？

## 五、Cowork：重点研究任务执行与信任

### 5.1 当前形态的重要变化

截至核对，官方说明 Cowork 与聊天正分批统一；不同账号仍可能看见不同入口。不要在面试中把固定的“Chat／Cowork 双标签”当作所有用户的现状。[当前变化](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude)

架构文档同时说明，当前默认在云端执行，既有桌面部署仍有本地执行情形。使用本机文件或浏览器时，要经桌面端连接和对应权限，设备离线就无法继续访问本机资源。[执行架构](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)

### 5.2 为谁服务

主要研究场景是知识工作者把一整项工作交给系统：处理一批文件、整理访谈、完成报告或办公成果。产品需要隐藏部分工程复杂性，同时保留用户对重要决定的控制。

### 5.3 典型流程

给出目标 → 连接资料或文件夹 → 确认可用权限 → 系统分步工作 → 用户在关键处补充或接管 → 检查、修改和使用成果。

官方产品指南强调本地资料、连接的云应用和浏览器等工作来源。[产品指南](https://claude.com/resources/guides/claude-cowork-product-guide/product-overview)

### 5.4 最有意思的产品取舍

**统一入口降低选择负担，也增加系统判断责任。**

当用户不再先选择“聊天还是执行”，系统需要判断：“帮我看看这个文件夹”是在咨询整理方法，还是授权实际移动文件？错误地把咨询升级为行动，会损害信任；错误地停留在建议，也会让任务落空。

**减少技术细节，需要更好的任务状态表达。**

知识工作者未必关心终端日志，但通常关心已经处理多少文件、是否漏项、是否还需要确认、结果放哪里。隐藏日志不能等于隐藏错误。

**文件访问方式会影响可完成的任务。**

上传副本、连接文件夹和通过浏览器处理在线资料，各自有不同的更新与保存关系。设计上应帮助用户理解系统正在操作哪个对象。

### 5.5 如果我是 PM，会做什么验证

以“整理 30 份资料”为例，预先确定分类规则、是否移动原件、是否允许改名、是否保留来源。完成后请用户在真实文件系统中找到三份指定材料，并继续使用它们。

衡量：分类正确率、找到材料耗时、错放和覆盖情况、用户纠正次数、下次是否愿意委托。

这些是建议实验，不是本材料已经进行的 Cowork 实测。

## 六、Claude Code：工程执行系统

### 6.1 产品入口已超过终端

官方概览包括终端、IDE、桌面和 Web 等入口，也提供继续本地会话、云任务和团队工作流的方式。需要分别核对执行位置，不能把手机可操作等同于代码在手机运行。[Claude Code 概览](https://code.claude.com/docs/en/overview)

**产品判断：**多入口的价值是任务连续性。代价是用户必须理解哪个环境持有文件、秘密和正在运行的进程。

### 6.2 指导、记忆和强制规则分开

Claude Code 文档区分人工编写的项目指导与自动记录的经验。它们作为上下文影响行为；要强制阻断某类操作，需要权限规则或适用的程序检查。[项目记忆](https://code.claude.com/docs/en/memory)、[权限](https://code.claude.com/docs/en/permissions)

**面试表达：**把要求写在 `CLAUDE.md` 或 `AGENTS.md` 中，是给系统指导；真正的执行边界需要由程序和环境控制。

### 6.3 权限模式影响用户怎样委托

官方列有手动、允许编辑、计划、自动审核等模式；具体默认和可用性要看当前入口与策略。它们改变工具动作如何被允许，不代表每种模式使用了不同模型。[权限模式](https://code.claude.com/docs/en/permissions)

**产品判断：**应该按任务风险选择交互，而非把“自动程度高”当成普遍更好。对低影响读写可减少打断，对不可逆外部动作需要更明确的决定点。

### 6.4 Subagents 和 Hooks

Subagent 有自己的上下文和工具范围，适合隔离专门子任务；程序事件机制则能在合适阶段做检查。两者解决的问题不同。[Subagents](https://code.claude.com/docs/en/sub-agents)、[Hooks](https://code.claude.com/docs/en/hooks)

**设计建议：**用子任务分担独立研究，用确定的检查验证确定的约束，再由人判断创意与业务质量。把所有检查都变成另一个模型的意见，仍可能漏掉同一种错误。

### 6.5 Checkpoint 的恢复范围

官方明确说明，检查点不追踪 Bash 命令造成的文件修改；部分子 Agent 的修改也不随主会话 rewind 恢复。应按实际范围理解，不能当作整个电脑和外部系统的撤销键。[检查点边界](https://code.claude.com/docs/en/checkpointing)

**产品判断：**恢复界面应告诉用户将恢复什么、仍保留什么。对已经发送或提交到外部的动作，还需要业务层的补偿办法。

## 七、Claude Code 与 Cowork 怎样比较

| 维度 | Claude Code | Claude/Cowork 任务执行 |
| --- | --- | --- |
| 分析时的主要用户 | 工程任务执行者 | 更广的知识工作者 |
| 典型验收对象 | 代码差异、运行、测试、工程交付 | 文档、表格、文件组织和跨工具成果 |
| 用户能接受的过程细节 | 命令、工具、配置、技术日志 | 目标、进度、关键决定和成品 |
| 常见风险 | 改错文件、运行环境、外部副作用 | 误解任务、误操作原件、成品缺漏 |
| 产品经理要问 | 改动正确且可维护吗？ | 用户能直接拿去完成工作吗？ |

这是工作重心比较，不是排他的功能边界。随着产品统一，同一个入口可能跨越两类任务。

## 八、商业化与长期使用：分析视角

- 个人订阅承接高频使用；组织方案需要额外提供协作、权限和管理价值。
- 开发平台提供另一条集成路径，产品收入与模型 API 使用不能混为一项。
- 会话、项目材料、可修改成果和复用流程，会增加使用连续性；与此同时应让用户容易找到、导出和纠正自己的资料。
- 执行越多，越需要解释资源消耗，避免用户只能靠等待猜测任务成本。

这里只分析商业结构，不给未经统一核验的套餐价格或 ROI。

## 九、面试可以提出的判断

> 我会重点观察 Claude 统一聊天和 Cowork 之后，是否真的减少了用户的选择成本，同时又清楚表达执行权限与任务状态。Code 更偏工程验收，知识工作还需要验证成果能否被真实使用。两者都需要让用户纠正系统，并理解恢复范围。

可接你自己的案例：反复生成完整剧本没有解决人物动机；按镜头裁剪角色信息；文件整理需要实际移动目录。把案例讲到具体决策，比只列出产品功能更有说服力。
