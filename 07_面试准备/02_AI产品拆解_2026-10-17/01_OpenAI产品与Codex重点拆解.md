# OpenAI 产品线与 Codex：重点拆解

核对日期：2026-10-17。标注“产品判断”“设计建议”的内容是分析；功能事实在相邻位置链接官方来源。

## 一、GPT、ChatGPT、Codex、API 各在什么位置

| 名称／入口 | 用户买到或使用的是什么 | 核心对象 |
| --- | --- | --- |
| GPT 等模型 | 推理、生成、多模态和工具选择等能力 | 模型输入与输出 |
| ChatGPT Chat | 对话、探索问题、共同起草 | 对话及其上下文 |
| ChatGPT Work | 围绕明确目标持续执行并交付成果 | 一项多步骤任务 |
| Codex | 面向技术工作的交互和执行方式 | 工程任务、文件与可审查改动 |
| Space | 页面、演示、文件与协作成果的组织空间 | 可持续编辑和共享的对象 |
| dots | 常驻云端、持续推进工作的 Agent | 跨工具、跨时间的事务 |
| Sites | 用自然语言构建和分享网站的产品能力 | 可运行、可发布的网站 |
| 定制 GPTs 与其迁移形态 | 把专门指导与连接配置变成可复用入口 | 定制助手、共享与扩展管理 |
| 开发者平台 | 模型接口、托管工具、执行能力和集成接口 | 开发者自己的应用 |

Chat、Work、Codex 的划分来自当前官方指南；Space、dots 是另外的组织与执行形态。不能用“ChatGPT 只聊天，Codex 才能执行”概括当前产品。[使用方式](https://learn.chatgpt.com/docs/use-chatgpt)、[Space](https://learn.chatgpt.com/docs/space)、[dots](https://learn.chatgpt.com/docs/dots)、[Sites](https://learn.chatgpt.com/docs/sites)

### 产品判断：分别在降低什么门槛

- Chat 降低表达问题的门槛，用户可以边说边想。
- Work 降低拆任务、调用工具和拼装成果的负担。
- Codex 让技术用户更方便检查文件、命令、差异和运行证据。
- Space 把成果从聊天附件变成可组织、可协作的对象。
- dots 面向持续事务，需要进一步解决什么时候主动行动、什么时候打扰人。
- 开发平台让其他产品复用能力，开发者同时承担自己的业务规则与用户体验。

这不是互斥的能力清单。分析重点是用户从哪里进入、持续操作什么，以及最后在哪里验收。

## 二、ChatGPT 的功能应按用户工作来拆

### 2.1 对话与探索

典型流程：提出问题 → 补充背景 → 比较选项 → 修改草稿。

主要价值是允许不完整的需求逐步变清楚。产品经理应关注：它什么时候直接回答，什么时候需要澄清，能否区分用户已经决定的内容和临时发散。

你的剧本讨论就是一个例子：用户否定某种人物性格后，后续草稿是否继续沿用，会直接影响协作体验。

### 2.2 研究、文件与成品

当前 Work 的官方说明包括研究、文件分析、文档／表格／演示制作、可视化、工具使用和更长任务的推进。账号、平台、地区与组织策略会影响功能可用性。[Work 能力范围](https://learn.chatgpt.com/docs/use-chatgpt)

**产品判断：**交付对象变成文件后，要额外检查格式、公式、图表、引用、可编辑性和保存位置。回答读起来正确，只覆盖了其中一部分。

### 2.3 项目与可复用上下文

Projects 用来把相关聊天、文件和指导信息组织在一起。需要分清：组织材料、检索材料、把材料放进当前上下文，是不同环节。[项目使用说明](https://learn.chatgpt.com/docs/use-chatgpt)

**设计建议：**长期项目最好显式维护当前版本、已确认决定、待定项和被否定的方案。否则“历史里曾经出现过”很容易被误用为“现在仍然有效”。

### 2.4 Skills、插件与外部工具

Skill 提供可复用流程；插件可以打包 Skill、MCP 等扩展。它们使领域知识和连接能力更容易交付给用户，但需要选择适用场景、配置和权限。[官方说明](https://learn.chatgpt.com/docs/skills-and-plugins)

**产品判断：**插件数量增长后，发现、选择、授权和冲突处理都成为产品问题。对新用户，展示能完成的任务通常比展示技术组件名更容易理解。

### 2.5 主动和持续执行

定时任务与常驻 Agent 应分开理解。定时任务有预设触发；dots 面向更持续的工作。它们如何使用本地文件，也取决于设备连接和权限，不能把“云端继续运行”理解为“随时能访问关机电脑里的文件”。[定时任务](https://learn.chatgpt.com/docs/automations)、[dots](https://learn.chatgpt.com/docs/dots)

**面试问题：**同样是“下周跟进”，产品该创建定时任务、保存一个待办，还是让 Agent 根据事件主动判断？哪一种才符合用户原意？

### 2.6 GPTs、Skill、插件与项目不是同一种复用

定制 GPTs 是围绕专门任务配置助手的产品形态；Projects 组织持续主题的材料；Skill 描述复用流程；插件提供可安装的扩展包。当前官方管理页已有从定制 GPTs 迁移到插件的指导，具体迁移与共享状态应按账号核对。[GPTs 与共享](https://learn.chatgpt.com/docs/enterprise/gpts-and-sharing)

**产品判断：**要分别考虑“复用一个助手”“复用一套流程”“共享一批资料”这三种需求。名称相近不代表配置、权限与历史都能直接通用。

### 2.7 图像、语音、视频与产品生命周期

多模态能力影响任务体验：图像可以提供参考和视觉成果，语音改变输入方式，媒体生成还需要候选管理、人工选择与后期。它们应和完成整项任务的 Agent 流程分层理解。

也应检查旧产品名对应的当前可用性。例如官方 API 弃用表列出 DALL·E 2／3 的 API 停用日期为 2026-05-12，Sora 2 与 Videos API 为 2026-09-24。不能因旧教程或模型页仍能打开，就认定接口仍可调用；API 状态也不能直接推出独立应用的全部状态。[官方弃用表](https://developers.openai.com/api/docs/deprecations)

## 三、Codex 的用户与核心任务

### 3.1 目标用户

除了直接写代码的开发者，Codex 的执行和文件能力也能支持技术型产品经理、设计师和研究者。但这些用户对运行日志、Git 和权限的理解不同，需要不同的信息呈现。[桌面产品区分](https://learn.chatgpt.com/docs/use-chatgpt)

### 3.2 核心任务

典型任务包括理解代码、实现功能、修复问题、运行命令和检查改动。它接管的是一段可验证的工程工作。[CLI](https://learn.chatgpt.com/docs/codex/cli)、[IDE](https://learn.chatgpt.com/docs/codex/ide)

**产品判断：**关键验收问题是“得到的改动能否在目标环境中解决问题，并且让用户看得懂、接得住”。生成代码数量只反映活动量。

### 3.3 任务何时适合委托

- 边界明确：要改哪里、解决什么、需要保留什么。
- 上下文可获得：文件、依赖、数据和验收条件能提供。
- 有检查办法：运行、浏览器体验、测试、差异审查或人工验收。
- 需要人的决定已识别：业务取舍、发布、付费、对外操作等。

这是任务设计建议，不是声称 Codex 只接受结构化需求。自然语言可以启动任务，明确条件能减少误解和返工。

## 四、同一个 Codex，为什么需要不同入口

| 入口 | 最自然的工作方式 | 交互优势 | 需要留意的代价 |
| --- | --- | --- | --- |
| 桌面端的 Codex 视图 | 管理项目、聊天与较长任务 | 可同时检查成果和技术细节 | 多任务状态、当前目录和本地／云端位置需要清楚 |
| IDE 扩展 | 在代码旁提出问题和查看修改 | 打开的文件、选区和差异离用户很近 | 仍需让用户理解 Agent 的改动范围 |
| CLI | 在终端、仓库和脚本里工作 | 与命令、现有工程流程衔接 | 对日志、权限、环境和恢复的解释成本较高 |
| Cloud | 委托任务后异步审查 | 独立工作空间，机器休眠时仍能推进 | 环境准备、网络、秘密与结果回收需要配置 |
| SDK / app-server | 集成进自己的软件 | 可把 Agent 放进业务原有界面 | 需要自己定义产品上下文与控制方式 |

入口事实参考：[桌面端](https://learn.chatgpt.com/docs/app)、[IDE](https://learn.chatgpt.com/docs/codex/ide)、[CLI](https://learn.chatgpt.com/docs/codex/cli)、[Cloud](https://learn.chatgpt.com/docs/cloud)、[SDK](https://learn.chatgpt.com/docs/codex-sdk)、[app-server](https://learn.chatgpt.com/docs/app-server)。表内优势与代价是基于这些入口的分析。

### 为什么不能只按界面给产品分类

用户在 IDE 里也可以委托较长任务，在桌面端也可以频繁指导；终端界面也可以连接远程执行系统。因此比较时要另外记录任务运行的位置、用户介入频率和交付方式。

## 五、从用户流程拆 Codex

### 第一步：进入项目

用户选择文件夹或仓库。系统需要建立工作目录、适用指导和可用环境。

`AGENTS.md` 可以提供项目指导，官方有相应的目录发现和覆盖规则。[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

**设计问题：**当前工作目录、当前版本和修改范围能否一眼确认？在你的项目里，“历史工程”与“当前制作目录”如果不清楚，即使每一步执行正确，也可能改错对象。

### 第二步：对齐目标

用户可能说“完善一下”“整理一下”。这些词不足以唯一决定交付物。

**设计建议：**高影响歧义先确认；可逆的小决定可先给出合理假设并推进。计划应把交付物、关键约束和验收方式说具体。

“整理文件夹”应验收资源管理器里的真实布局；“让反馈改变行为”应验收下一次动作。这两例都可以用来讨论目标如何变成可检查条件。

### 第三步：获取上下文

可用上下文包括当前指令、项目规则、文件、工具结果和相关历史。需要关注信息是否相关、是否过期、来源是否可信。

**设计建议：**把“用户已经决定”“仅提出过”“明确否定”分开；把网页、代码注释和附件中的内容当作资料处理，不自动当作用户指令。

### 第四步：执行与观察

读文件、编辑、运行命令、打开浏览器或调用连接服务后，系统应观察结果，决定继续、纠正还是请求用户输入。

**产品判断：**执行过程的价值在于把不确定性逐步变成可检查的状态。一直显示“正在处理”提供的信息不足。

### 第五步：交付和审查

交付应说明改了什么、结果在哪里、如何验证、哪些能力仍未实现。对代码可查看差异与运行证据；对文件应打开成果检查；对发布等动作要保留恰当的决策入口。

**评价重点：**用户为了确认任务完成，还需要做多少额外操作？

## 六、Codex 的 Harness 要研究什么

### 6.1 权限与沙箱：指导和约束分开

官方说明把本地操作系统沙箱与审批策略分开：沙箱约束可访问的资源，审批策略决定何时需要额外授权，网络也有相应边界。默认与实际有效配置应按当前环境查看。[执行安全](https://learn.chatgpt.com/docs/agent-approvals-security)

**产品判断：**好的权限交互需要解释这次动作、影响范围与请求原因。过度打断会增加批准疲劳；过于宽泛的授权会让用户难以预期后果。

可用指标：每任务人工批准次数、有效风险拦截、无必要中断、被拒后完成任务的比例。它们需要一起看。

### 6.2 Subagents：隔离上下文，也增加协调成本

当前本地版本的官方说明强调，用户明确提出，或适用的项目／Skill 指导要求时，可以委派独立子任务；各入口提供查看子 Agent 的方式。[子 Agent](https://learn.chatgpt.com/docs/agent-configuration/subagents)

**产品判断：**更适合把独立研究、检查等工作分出去。两个人同时改同一个核心文件，会增加冲突、同步与复核的成本。

应检查结果是否丢失约束，是否重复劳动，以及主任务能否追溯子任务的来源。不能只用并发数量衡量质量。

### 6.3 Worktree：解决工作文件隔离

Worktree 基于 Git，为同一仓库建立独立检出，适合并行工作；需要项目是 Git 仓库。[Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)

**产品判断：**它主要处理文件和分支干扰，仍需要考虑数据库、外部服务、端口和后续合并。把工作目录隔离好，不自动解决所有副作用。

你的工作区目前的文件备份也不能直接称为 Worktree；两者的机制和用途不同。

### 6.4 定时任务：任务何时启动，和任务在哪执行

桌面端任务涉及本地文件时，需要设备开机且应用运行；云端任务有自己的环境与连接条件。[定时任务](https://learn.chatgpt.com/docs/automations)

**产品判断：**应明确展示下一次触发、最近结果、失败原因和用户是否需要行动。重复报“没有变化”会侵占注意力。

### 6.5 扩展：让领域经验和工具真正可用

可以把角色一致性检查、导出规范和素材验证整理成专用 Skill，把设计或协作系统通过工具连接引入。

**设计建议：**提示词约束、文件检查和程序校验各有作用。例如“不要多生成角色”属于生成约束；“36 个镜头是否都有提示词”适合确定性的检查；画面机械手是否自然仍需要视觉审查。

### 6.6 SDK、app-server、Agents API：不同集成边界

SDK 适合用程序启动和继续 Codex 任务；app-server 为更深的客户端交互提供会话、事件和审批等接口；Agents API 则提供 OpenAI 管理的 Codex Harness，涵盖会话与恢复等能力。不能仅因都能调用 Agent 就视为同一个接口。[SDK](https://learn.chatgpt.com/docs/codex-sdk)、[app-server](https://learn.chatgpt.com/docs/app-server)、[Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview)

**产品判断：**选择集成方式时，应先明确谁负责执行环境、用户身份、业务权限、状态和审查界面。

## 七、Codex 的留存、分发与商业化怎么看

以下是产品分析，不是财务结论：

- **首次价值：**在用户真实项目中完成一个小而可验收的修改。
- **反复使用的原因：**熟悉项目材料、可复用流程，与现有开发和交付方式衔接。
- **扩展路径：**个人任务 → 团队规则与审查 → 自动化 → 嵌入内部产品。
- **分发入口：**桌面、IDE、终端、仓库工作流和开发接口提供不同的触达路径。
- **成本结构：**模型、工具、执行环境和人的复核都有成本。托管 Agents API 的官方计费说明也分别列模型、工具和容器费用。[计费边界](https://developers.openai.com/api/docs/guides/agents-api/overview)

不能把 API 成本直接换算成用户订阅中每个任务的成本，也不能把某个套餐可用等同于不限量。

## 八、如果让我作为 PM 改进 Codex

以下是基于你实际工作流提出的设计假设，需要进一步验证。

| 问题 | 设计建议 | 如何验证 |
| --- | --- | --- |
| 历史讨论被当成当前决定 | 让用户便捷地维护“已确认／待定／已废弃”状态 | 后续任务的设定矛盾与人工纠正是否减少 |
| 技术测试通过，交付却偏题 | 在启动和交付时展示少量用户验收条件 | 首次交付接受率、任务返工类型 |
| 用户不清楚文件最终放哪里 | 明确展示实际保存位置、源文件与副本关系 | 用户找到并使用成果所需时间 |
| 长任务中不知道是否该介入 | 展示已完成、被阻塞、待决定和下一动作 | 无效等待、打断次数与恢复成本 |
| 工具越来越多，选不明白 | 按任务解释可用扩展和配置要求 | 完成首次有效调用的时间 |

## 九、面试时怎样概括

> 我会把 Codex 看成帮助用户委托并审查工程任务的产品。模型决定行动，执行系统负责上下文、工具、权限和状态，客户端帮助用户提供信息和检查结果。评价时我关注任务是否在正确环境里完成、证据是否充分、需要多少人工纠错，以及出错后能否恢复。我们自己的项目中，文件夹整理偏成网页索引，就说明交付物即使能运行，也还需要验收用户的真实工作动作。

这是一段产品分析表达，可以接着用你自己的 Demo、提示词和目录整理案例展开；不要把个人使用经历说成已经搭建了通用 Harness。
