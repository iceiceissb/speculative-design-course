# 横向比较：把功能介绍变成产品判断

本篇是基于前述官方资料的综合分析。没有统一实测，因此不提供“最强”“最便宜”或百分制排名。

## 一、先比较任务入口与交付方式

| 产品／入口 | 用户通常怎样开始 | 用户主要操作什么 | 应重点检查什么 |
| --- | --- | --- | --- |
| ChatGPT Chat | 提问题、给背景 | 对话与草稿 | 理解、事实、引用、方向 |
| ChatGPT Work | 描述需要完成的成果 | 任务、资料与文件 | 完整性、成品和剩余事项 |
| Codex | 选择项目，提出技术任务 | 文件、工具、差异与任务状态 | 正确环境、执行证据与可接手性 |
| Claude 对话／Artifacts | 共同讨论或创建成果 | 对话旁的可编辑对象 | 内容与实际可操作性 |
| Claude/Cowork | 交给系统一项知识工作 | 文件、连接工具与完成对象 | 访问范围、目标对齐和成品 |
| Claude Code | 在工程环境中提出任务 | 代码、命令、指导与会话 | 测试、权限与恢复范围 |
| Cursor | 继续编辑，或委托 Agent | 选区、文件和工程任务 | 局部效率、上下文和改动范围 |
| OpenCode | 选择配置、模型和任务 | Agent 会话及执行服务 | 配置、有效权限和模型适配 |
| GitHub Copilot | IDE／终端／仓库中的请求 | 代码、Issue、分支和 PR | 团队审查与交付负担 |
| Manus | 委托目标和材料 | 执行中的任务与成果 | 结果质量、复核和资源消耗 |
| OpenClaw | 从消息等渠道发送请求 | 会话、Gateway、设备和工具 | 身份、持续运行和通知价值 |
| Hermes Agent | 提任务并持续积累经验 | 会话、记忆和 Skill | 经验是否有效、可纠正 |

表格只描述研究重心。产品入口和当前功能事实见各产品篇，不能据此推断某产品没有另一家的能力。

## 二、六组面试里很值得比较的问题

### 1. Codex 与 Claude Code：不要只回答哪个更会写代码

可以比较：相同仓库中怎样找上下文，如何计划与执行，什么时候打断人，怎样展现差异和测试，失败后怎样继续，以及与现有工作流怎样衔接。

**可表达的判断：**模型能力会影响结果，执行环境、工具设计和审查体验也会影响用户最终获得的价值。要知道差异来自哪里，需要控制模型、任务和环境等变量。

### 2. Cursor 与 Claude Code：都能用模型，产品为什么仍有差别

正在编辑时，选择文件、光标位置、错误提示和接受建议都是低成本操作；终端式工作更接近直接委托工程动作。两家又都扩展到了更多入口，因此应比较具体使用流程。

**关键问题：**用户想亲自操作哪一部分，愿意交出去哪一部分？任务频率与跨度如何影响入口选择？

### 3. Copilot 与 Cursor：现有团队流程会改变产品价值

个人输入速度和团队交付速度可能不同。IDE 里快一些，如果换来更多审查和回滚，就未必改善整体效率。

**关键问题：**任务从哪里来，结果返回哪里，谁负责审查，现有仓库规则如何影响 Agent？

### 4. Cowork、ChatGPT Work 与 Manus：知识工作怎样验收

它们都在覆盖多步骤任务。需要比较输入资料的方式、执行位置、进度和接管，以及成果能否在用户原来的工具里继续使用。

**关键问题：**用户要求“整理资料”时，系统应该返回建议、创建副本还是移动原件？界面如何让双方形成相同预期？

### 5. OpenCode 与托管产品：控制权和准备负担如何取舍

模型、工具和客户端更可配置，可以支持特定需求，也需要处理组合、版本和排错。

**关键问题：**哪些东西应预设为可用，哪些配置应留给高级用户？首个成功任务要经历多少步骤？

### 6. OpenClaw、Hermes 与常驻托管 Agent：运行得久有什么价值

长期运行有价值的前提，是相关事务真的被推进、重要变化及时到达、旧经验没有造成新错误。

**关键问题：**触发条件、身份、记忆、通知、资源消耗和暂停机制怎样让用户理解并控制？

## 三、一个任务拆开后，人到底承担多少工作

```text
提出需求
  → 整理上下文
  → 配置环境和工具
  → 观察执行
  → 在关键处做决定
  → 审查结果
  → 修正与接手
  → 发布或实际使用
```

评价提效时，把这些阶段都算进去。

例如：Agent 生成初稿只用十分钟，用户却用了两小时核实引用、改格式和找文件，不能只报告前十分钟。反过来，执行时间较长，但用户能安心离开且成果几乎不用返工，也可能更有价值。

## 四、三个容易混为一谈的“上下文”

| 类型 | 例子 | PM 要关注 |
| --- | --- | --- |
| 当前任务输入 | 这次需求、选中的代码、引用的镜头 | 是否充分、相关、无歧义 |
| 可检索的项目知识 | 人物设定、规范、历史素材 | 能否找到正确版本，能否追溯来源 |
| 任务执行状态 | 已完成步骤、工具结果、任务 ID | 能否继续、恢复和防止重复动作 |

长上下文窗口主要增加一次可提供的信息容量；项目资料、持久记忆和执行状态则需要自己的组织与更新机制。

**结合你的例子：**“徐月禾的外貌”可以保存在角色库，但只有当镜头需要时才提供具体描述；“这个镜头没有她”是当前任务约束；“上一候选已经生成、是否选用”是执行状态。

## 五、权限、沙箱、审批、恢复，分别检查什么

| 机制 | 应回答的问题 | 不能自动覆盖的问题 |
| --- | --- | --- |
| 权限规则 | 这个动作是否允许 | 动作是否符合真正需求 |
| 沙箱 | 执行能接触哪些资源 | 所有副作用都能否撤销 |
| 人工审批 | 用户是否愿意接受这次动作 | 用户有没有看懂影响 |
| 自动风险审核 | 动作是否符合配置和已知约束 | 模型判断是否永远正确 |
| 检查点／版本控制 | 哪些状态可以恢复 | 已发生的外部业务后果 |
| 重试与继续 | 中断后怎样推进 | 是否会重复付款、发送或提交 |

这些是比较问题，各家的实现范围需看产品篇。Claude Code 的检查点文档尤其适合说明恢复有具体边界。[恢复范围](https://code.claude.com/docs/en/checkpointing)

## 六、建议的指标体系

### 6.1 全流程指标

| 指标 | 一种可操作的定义 | 注意事项 |
| --- | --- | --- |
| 成功交付率 | 达到预先约定验收条件的任务数 / 已启动任务数 | 明确取消、阻塞、超时怎样计入 |
| 首次交付接受率 | 首次交付后无实质返工的任务数 / 首次交付任务数 | 文案小改与逻辑重做应区分 |
| 端到端耗时 | 从用户开始准备任务到成果可用 | 包括配置、等待、复核和修正 |
| 人工介入负担 | 次数与实际耗时，按类型拆分 | 有价值的业务决定不能一律当失败 |
| 恢复成功率 | 被中断后按原目标完成且未重复副作用的比例 | 可用模拟环境测试 |
| 每次成功交付成本 | 模型、工具、环境与人工成本 / 验收通过的交付数 | 分母失败时不要只报告便宜单次调用 |

### 6.2 不同产品重心对应的补充指标

- **编辑建议：**接受后保留程度、撤销、错误引入、感知延迟。
- **工程委托：**测试和人工验收、审查耗时、合并后缺陷与回滚。
- **知识工作：**事实与引用、覆盖、格式、可编辑性、返工负担。
- **研究：**来源支持、时效、漏项、缺失数据处理。
- **长期 Agent：**有用提醒、误报、漏报、重复操作与记忆纠正。

以上是建议口径，不是各家已经公布或内部采用的指标。

## 七、做商业化分析时别只比较月费

应该拆成四个问题：

1. **为什么付费？**更高成功率、更少复核、更长任务、协作治理，还是某个高价值集成？
2. **谁付费？**个人、团队、企业，还是开发者应用的拥有者？
3. **消耗怎样变化？**模型、执行时长、工具、并行任务和环境会怎样增加成本？
4. **用户怎样预测？**启动前、执行中和完成后分别能知道什么？

Manus 的 Credits 说明列出模型、虚拟机与第三方 API；托管 Agent 接口也涉及多类资源计费。它们都提示我们研究成功任务的总成本，而非只比较一个标价。[Manus](https://help.manus.im/en/articles/11711097-what-are-the-rules-for-credits-consumption-and-how-can-i-obtain-them)、[OpenAI Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview)

## 八、面试常见问题：建议的回答结构

### Q1：你怎么理解 Harness？

> 我把它理解成模型周围的执行系统：准备上下文、暴露工具、管理会话与状态、执行权限检查、接收工具结果，并处理失败和交付。界面帮助用户输入目标和接管，模型负责生成与决策，执行边界不能只靠提示词维持。具体哪些部分由平台、业务应用和用户负责，需要看实现。

可用 Codex app-server 与 OpenCode Server 说明客户端和执行接口，再用权限模式说明规则怎样作用于实际动作。[Codex](https://learn.chatgpt.com/docs/app-server)、[OpenCode](https://opencode.ai/docs/server/)

### Q2：为什么不能让模型一直自主做下去？

> 有些缺失信息或业务取舍只有用户知道，有些动作成本高或难恢复。我会识别这些决定点，让系统在其余可确定步骤继续推进。目标是减少无效打断，同时保留真正有意义的控制。完成后还需要按用户目标验收。

### Q3：模型能力和产品能力怎样区分？

> 可以分别控制变量：同样的模型换执行方式，看上下文、工具和验证是否改善结果；同样的执行条件换模型，看工具使用、质量、延迟和成本的变化。端到端产品效果还包括用户准备与复核的负担。

### Q4：多 Agent 有什么价值？

> 可以并行独立任务，也可以隔离噪声上下文。但有协调、汇总、冲突和重复调用的成本。我会先找出任务之间的依赖，保留主任务的约束，再验证整体成功率和总成本。

### Q5：你自己有哪些一手体验？

可以从三件事展开：

- 发现轮椅 Demo 没有把反馈落实成下一次行为，于是把要求改成可比较的执行状态。
- 发现未出镜人物的外貌描述导致多生成角色，改为按镜头提供上下文。
- 发现网页索引没有满足整理文件夹的需求，增加真实目录布局和移动后可用性的验收。

然后说明人负责的选题、判断、纠正和验收，以及 AI 辅助实现的部分。现有状态机 Demo、接入接口和真实自主 Agent 要分开讲。

### Q6：如果给 DeepSeek 做产品，你会先做什么？

> 我会先选一个明确人群和高频任务，收集完成过程中的真实失败，区分是模型、上下文、工具、环境还是交付出了问题。先做一个可验收的闭环，再选择最值得投入的执行能力和入口。不同人群需要的首个成功体验可能不同，不必一开始就复制一个很大的通用 Agent。

这是通用产品研究思路，不是对 DeepSeek 未公开路线的判断。

## 九、你接下来最值得形成的观点

**“我会评价 Agent 是否替用户完成了工作，也会计算为了让它完成，用户额外承担了多少准备、判断和纠错。”**

这句话可以把产品体验、Harness 机制、效果评估和你自己的项目连起来。它需要具体例子和记录支持，而不是只作为口号。
