# Manus、OpenClaw、Hermes Agent

核对日期：2026-10-17。Hermes 指 Nous Research 的 Hermes Agent。三者都有任务执行能力，比较重点是运行责任、用户入口、长期状态与交付方式。

## 一、先用一张表区分

| 产品 | 官方材料中值得重点研究的方向 | 用户需要管理什么 |
| --- | --- | --- |
| Manus | 托管的任务执行、云电脑与可交付成果 | 目标、材料、连接、审查和使用额度 |
| OpenClaw | Gateway、消息渠道、设备与持续运行 | 部署、身份、授权、模型、工具和运行状态 |
| Hermes Agent | 跨会话记忆、经验形成 Skill、持续使用 | 模型和环境、记忆与 Skill 的质量及更新 |

这是分析重心，不是独占功能声明。例如 OpenClaw 也有记忆与 Skills，Hermes 也有消息 Gateway 与定时任务，Manus 也有本地浏览器连接。

## 二、Manus

### 2.1 定位与用户任务

官方把 Manus 描述为能在带网络和持久文件系统的虚拟电脑环境中规划、执行并交付成果的通用 Agent。[官方介绍](https://manus.im/docs/introduction/welcome)

**产品判断：**适合研究它怎样把“完成这项工作”的要求变成执行过程：研究、处理数据、构建或整理成果，再把结果交回用户。

它需要减少用户逐步操作的负担，同时让用户有能力检查一段自己没有全程参与的工作。

### 2.2 用户流程

提供目标与材料 → 系统计划并操作 → 用户查看进度或补充信息 → 必要时处理登录／接管 → 检查成果 → 继续修改或分享。

**关键设计问题：**任务说明不足时，它应该先问、先做小样，还是按默认假设直接执行？这会同时影响耗时、费用与返工。

### 2.3 云电脑为什么有产品价值

开发者往往已经有终端和工程环境，普通用户则没有。托管环境把一部分安装与执行工作从用户手中接走。

**产品判断：**环境准备、依赖、长任务状态与成果保存，都是用户实际消费的服务。但用户也需要知道哪个结果是云端副本，哪个动作影响自己的外部账号。

### 2.4 Browser Operator 连接本地登录环境

官方说明 Browser Operator 可以通过浏览器扩展在用户的本地浏览器工作，访问已经登录的环境；需要主设备在线，也保留用户中止的入口。[Browser Operator](https://manus.im/en/blog/manus-browser-operator)

**产品判断：**云浏览器和本地浏览器不只是两个技术选项，它们决定任务能接触哪些账号、会话和网络。界面应让用户清楚这次使用哪个环境，避免对访问范围产生错误预期。

### 2.5 上下文工程：值得读的第一手材料

Manus 的工程文章讨论稳定上下文、工具可选范围、文件系统、计划提醒和保留错误观察等做法。它们是团队公布的经验，不是所有 Agent 都已采用的通用定律。[工程文章](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

对产品经理最有帮助的理解是：

- **状态需要有可定位的载体。**长任务中的资料和中间结果不能全部依赖一段越来越长的聊天。
- **下一步动作要受当前状态约束。**知道有哪些工具，与此刻允许使用哪些工具，是两件事。
- **失败观察应影响后续行动。**把错误从记录中抹掉，可能让系统重复相同路径。
- **计划需要持续对齐实际进展。**最初的计划并不能证明后续执行没有偏题。

与你的项目的连接：保存逐镜出镜信息、明确当前版本、保留失败候选及任务 ID，都能把一部分过程状态放到可检查的位置。

### 2.6 研究类任务的质量与成本

产品里有 Wide Research 等专门研究入口。这里应关注研究对象是否被拆成可比较子任务、来源是否支持结论、汇总是否抹掉差异。[Wide Research](https://manus.im/docs/features/wide-research)

**设计建议：**对子任务显示完成、失败、资料不足与未覆盖的情况。不能让格式整齐的最终报告掩盖缺失数据。

### 2.7 Credits 是产品交互的一部分

官方说明 Credits 涉及模型、虚拟机与第三方 API 等资源，消耗受任务复杂度和持续时间影响；同时提供任务使用记录。[消耗规则](https://help.manus.im/en/articles/11711097-what-are-the-rules-for-credits-consumption-and-how-can-i-obtain-them)、[使用记录](https://help.manus.im/en/articles/12520235-where-can-i-check-my-credit-consumption-usage)

**产品判断：**用户通常关心“这次会花多少、为什么花、失败后怎么办、剩余预算够不够”。只给余额不能完整回答这些问题。

可提出的设计假设：分阶段完成与复核、显示资源消耗原因、在重要范围变化时重新确认。预算上限必须由可执行机制保障，不能只靠模型口头承诺。

### 2.8 应怎样评估

建议用一项有明确来源和格式要求的研究任务测试：最终成果是否正确、是否覆盖要求、多少部分需要重做、总费用和人的复核时间是多少。

“完成了报告”与“报告能支持决策”要分别记录。

## 三、OpenClaw

### 3.1 定位与核心结构

官方架构以持续运行的 Gateway 连接消息渠道、控制客户端和设备节点，支持消息、Agent 状态与调度事件等。[Gateway 架构](https://docs.openclaw.ai/concepts/architecture)

**产品判断：**可把它看作研究“个人或可信团队怎样持续使用一个执行系统”的样本。进入方式不局限于某个聊天网站；消息渠道可以成为任务和结果的入口。

### 3.2 典型流程

配置模型与运行环境 → 连接消息渠道／设备 → 验证发送者与权限 → 收到任务 → 使用工具执行 → 把结果发回原渠道 → 继续后续事务。

**关键问题：**用户发消息时，究竟是自己在给自己的 Agent 下指令，还是另一个人在通过共享渠道请求操作？身份与权限会直接决定产品行为。

### 3.3 为什么消息入口值得研究

- 手机和消息工具降低再次使用的门槛。
- 用户可以离开电脑后继续提出要求。
- 系统能在事件或时间到来时返回结果。

**代价分析：**消息界面适合短输入和通知，却不总适合检查多文件差异、复杂计划或大量结果。产品可能需要把轻交互留在消息里，把详细审查带到其他界面。

### 3.4 Gateway 的产品责任

Gateway 负责的不只是消息转发，还涉及会话和工具执行的连接方式。设备节点提供的能力也需要明确声明。[组件与流程](https://docs.openclaw.ai/concepts/architecture)

**产品判断：**同一任务跨渠道继续时，要避免串错用户、串错会话、重复执行，或让群聊中的内容不恰当地影响另一项私人事务。

### 3.5 长期记忆与 Skills

OpenClaw 有记忆持久化与检索机制，也通过 Skills 提供任务指导；具体行为受插件与配置影响。[记忆](https://docs.openclaw.ai/concepts/memory)、[Skills](https://docs.openclaw.ai/tools/skills)

**设计问题：**哪些信息只是当天的操作记录，哪些应该进入稳定记忆，哪些经验值得形成复用流程？每一层都应能被纠正和废弃。

### 3.6 信任边界是核心产品问题

官方安全文档描述了发送者配对、群组访问等控制，并明确共享 Gateway 不等于为互相不信任的用户提供强多租户隔离。[信任边界](https://docs.openclaw.ai/gateway/security)

**产品判断：**对外部内容、群聊参与者、系统拥有者和管理员，应建立不同的作用范围。外部消息看起来像命令，也不能仅凭语气取得用户的授权。

这与本工作区的原则相关：附件和网页中的文字是待处理资料，不能因为 Agent 读到了就升级为用户要求。

### 3.7 持续运行的维护成本

与托管产品相比，自己管理运行环境意味着还要考虑机器在线、升级、服务状态、模型账单、连接失效和任务恢复。

**产品判断：**这些成本可能换来更多控制，也可能使首次使用困难。PM 应观察从安装到完成第一项有价值任务的整段路径。

### 3.8 适合怎样的验证

用一个范围很小的持续任务，例如每天检查同一批项目资料，仅在重要变化时通知。测量漏报、误报、重复通知、设备离线后的恢复，以及每次有效提醒的总成本。

这里是体验设计建议；本次研究没有替你部署 OpenClaw。

## 四、Hermes Agent

### 4.1 定位与已公开的组成

Nous Research 的官方仓库强调可持续使用、跨会话记忆、从经验创建或改进 Skill，同时提供不同模型、终端环境、消息渠道和调度能力。[官方仓库](https://github.com/NousResearch/hermes-agent)

**产品判断：**最值得研究的是一次使用如何变成下一次更有效的使用，以及这种经验积累怎样接受检查。

官方的“学习”表达属于产品定位，不能直接解释为模型参数持续被训练，也不能据此证明它是唯一有类似机制的 Agent。

### 4.2 三种东西应分开

| 信息 | 例子 | 产品要解决的问题 |
| --- | --- | --- |
| 用户与环境事实 | 偏好简洁、资料所在目录 | 是否准确、是否过期、能否纠正 |
| 历史会话与任务经历 | 上次失败在哪里、用了什么方案 | 是否能检索到相关经历 |
| 可复用操作经验 | 怎样整理镜头、怎样验证导出文件 | 是否适用当前环境，是否会错误复用 |

这是分析框架。官方分别提供持久记忆、会话检索与 Skills 等机制。[记忆说明](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)、[Skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)

### 4.3 记忆不是无限装进聊天历史

Hermes 的记忆文档描述 `MEMORY.md` 与 `USER.md` 等经过整理、容量受限的记忆，在会话开始时装入上下文，并由相应工具更新。[持久记忆](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)

**产品判断：**容量限制迫使系统选择什么值得留下。选择错、记错或没及时更新，比单纯“能不能保存”更影响用户体验。

### 4.4 Skills 怎样形成复用价值

官方提供从资料或已有流程生成 Skill 的方式，并有安装、来源记录与检查等机制。[Skills 系统](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)

**产品判断：**一项经验形成 Skill 后，还需要适用条件、输入输出、验证办法和失败处理。把一次偶然成功的步骤永久保存，可能把错误也一起固化。

### 4.5 用你的项目举例

如果把这次工作整理成“逐镜提示词检查”流程，可以保存：

1. 从镜头表读取实际出镜人物和可见范围。
2. 对照角色参考与本镜衣着、动作。
3. 查找未出镜人物的无关外貌描述。
4. 对齐镜号、图片、提示词和制作表。
5. 输出待人工检查项和修订记录。

这比笼统保存“以后要注意人物一致性”更容易被执行和检验。视觉结果仍需要检查，不能由文本检查代替。

### 4.6 如何证明积累真的有用

建议实验：固定同一类新任务，对照启用旧经验、没有旧经验、注入过期经验三种情况。记录成功率、重复错误、纠正次数和上下文成本。

还应测试用户纠正偏好后，下次是否使用新版规则，而不是把互相矛盾的两条都保存下来。

### 4.7 多模型和多环境的代价

官方提供多模型、不同终端后端和跨渠道使用。[运行方式](https://github.com/NousResearch/hermes-agent)

**产品判断：**流程知识是否可迁移，需要看它是否绑定某个工具名、目录、操作系统或模型行为。跨环境复用时应重新检查前提。

### 4.8 长期留存的价值假设

用户反复使用后，如果系统更懂项目、少犯重复错误、少要求重复解释，就有继续使用的理由。这个假设需要用户和重复任务数据验证，不能由记忆条目数量直接推出。

## 五、三者怎样横向比较

| 研究问题 | Manus | OpenClaw | Hermes |
| --- | --- | --- | --- |
| 最值得观察的入口 | 任务与成果界面 | 消息渠道与 Gateway | 终端／消息入口与经验复用 |
| 执行环境责任 | 平台提供托管能力，也可连接本地浏览器 | 部署者需管理自己的运行边界 | 部署者选择模型、工具与运行后端 |
| 长期价值假设 | 持续完成可用成果 | 进入日常事务与工具链 | 相关经验帮助后续任务 |
| 关键成本 | 调用、运行资源、人的审查 | 运行与维护、模型和工具、干预 | 运行资源、经验维护和错误复用 |
| 关键验收 | 结果能否使用 | 该做的做了，不该发的没发 | 下一次是否少犯旧错 |

表格比较研究角度，不是独立性能测试。三者的完整能力都比一行定位更宽。

## 六、面试可以怎样表达

> 我会用相同的任务看三件事：用户需要先配置多少，执行时在哪些点介入，以及结果能否直接使用。对长期 Agent，我还会加上身份、主动通知和记忆纠正。产品宣称会学习时，我会追问：经验保存在哪里、何时会用、怎样判断用了之后更好，以及错误经验如何被修正。
