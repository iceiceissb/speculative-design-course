# 工作流经历：AI 产品与 Agent Harness 两个方向

整理日期：2026-10-17。岗位侧重点依据你提供的截图；以下评价是结合现有项目材料作出的判断，不代表招聘方的录用标准或项目已经完成的商业验证。

## 一、可以讲，而且有几件事值得深入讲

最有支撑的定位是：**从一个真实创作任务出发，在 AI 辅助下做出可运行原型，并在实际使用中发现失败、提出约束、调整工作方式。**

你有自己提出的选题、反复追问的体验问题、可以打开的交付物，以及修改前后的记录。接下来需要把“用了哪些工具”整理为“做了哪些判断，这些判断改变了什么”。

这段经历现在可以支撑 AI 产品使用深度、原型推进和部分 Harness 实践。对真实用户需求、多人使用、统计实验、线上质量和商业价值，还需要补证据。

## 二、最适合讲的三个片段

### 1. 用户反馈要改变下一次行动

**你发现的问题：**轮椅 Demo 能选择、拒绝、看到回应，但走完整个故事后，使用者看不到这些反馈究竟影响了什么。

**你的产品判断：**“机器人说自己记住了”不足以说明调整发生。体验需要显示前次行为、人的反馈、下一次实际执行，并允许比较是否履行。

**现在有的材料：**D07 的六幕选择、跨幕记忆、结尾行动规则、坡道助力的状态变化，以及采纳／坚持原策略的不同结果。D06 保留此前打包的版本，可比较代码与界面。

**适合追问：**如何定义一次有效反馈？拒绝之后系统是否仍然偷偷替用户行动？如何检验文字承诺与执行状态一致？

**准确边界：**这里是预设分支和程序状态更新，没有接入真实轮椅，也不是大模型在线学习或训练。

### 2. 人物设定越全，某些镜头反而越容易出错

**你发现的问题：**有些镜头没有徐月禾，提示词却保留她的外貌，视频会补出一个像她但又不一致的角色。

**你的产品判断：**需要根据每个镜头实际可见的人物提供上下文。单人、远景虚焦和仅露出袖口等情况，应使用不同程度的信息。

**现在有的材料：**F07 中 36 镜按出镜范围整理的提示词，以及 F10 保存的修改前文件。36 镜对应图片、提示词、JSON 和制作表都有记录。

**适合追问：**哪些信息应全局继承？哪些应随任务裁剪？如何防止“参考资料”被模型当成“这个镜头要生成的内容”？

**准确边界：**修改已落实到提示词和文件；没有受控的同模型、同参数前后对照，不能据此声称角色错误率降低了某个百分比。

### 3. “整理文件夹”被执行成“做一个网页索引”

**这次实际发生的问题：**你要求整理工作区，首次交付侧重版本复制和网页检索，旧目录仍然散落在根目录。网页可用、链接检查通过，却没有满足你直接在资源管理器中找文件的工作习惯。

**你的产品判断：**验收应包含任务发生的真实界面与使用动作。这里的交付条件包括根目录按用途编号、文件实际移动、旧工程与当前材料分开、移动后仍可运行。

**现在有的材料：**两次整理记录、本次迁移计划、实际移动日志、路径修复和移动后的运行检查。

**适合追问：**Agent 在执行前应确认哪些歧义？怎样避免把容易做、容易测的交付物当成用户真正要的结果？

这一例既能说明你的体验判断，也能说明验收集本身要随真实失败修订。

## 三、AI 产品经理方向怎么组织

建议以《不用麻烦她》的交互原型为主案例，把创作工作流作为实现方法。

| 要表达的能力 | 当前可以展示的材料 | 需要补充的证据 |
| --- | --- | --- |
| 发现问题、明确需求 | 从“尊重意愿”推进到可见的选择、拒绝和行为变化 | 老年人及照护相关真实使用者的访谈或观察；目前角色并非实地研究结论 |
| 交互设计与落地 | 可运行 Demo、界面、状态与跨场景影响 | 让没看过项目的人操作，看能否理解并完成流程 |
| 判断模型能力边界 | 机械手错误、人物误生成、情节反复变平淡 | 错误分类与对照样例，区分脚本问题、提示词问题和模型输出问题 |
| 推进迭代 | 教师反馈、用户自己的纠正、版本材料 | 选择两三次关键决策，解释取舍；大量版本本身不能证明迭代有效 |
| 数据意识 | 已有程序验证和生成／选择记录 | 定义成功标准，并补一个小规模、可复核的比较实验 |

### 约 60 秒的开场

> 我从以前做过的轮椅项目出发，做了一个关于智能轮椅怎样介入老人社交的思辨设计。我负责选题、人物关系和体验判断，用 AI 辅助完成原型、分镜和制作工具。过程中最关键的一次修改，是我发现原型虽然允许用户反馈，但反馈并没有清楚地改变下一次行动，所以我们把它做成了可比较的执行结果。另一个问题是视频提示词带入了未出镜人物的设定，我据此把上下文改成按镜头提供。这个项目让我开始关注 AI 产品怎样让用户表达意愿、纠正错误，并确认系统真的执行了修改。目前它是单人创作和课堂原型，我还没有把它作为已验证的老年用户产品来讲。

## 四、Agent Harness 方向怎么组织

建议以“让一个已有 Coding Agent 持续完成多步骤创作”为主案例，展示上下文、执行状态、恢复与验收。

OpenAI 官方把 Harness 描述为围绕模型管理上下文、工具、进度、失败与必要审批的执行系统。我们使用了现成 Harness，并在项目层整理规则、材料和验证条件；目前没有自行实现通用 Harness。[官方说明](https://developers.openai.com/blog/codex-as-a-platform)

| Harness 相关问题 | 项目中已有的实践 | 讲述时的边界 |
| --- | --- | --- |
| 长任务怎样保持状态 | 明确人物设定、当前共识、待定项、版本与来源 | 文件化项目状态；不宣称模型天然记住所有历史 |
| 工具怎样接入任务 | 本地文件、制作脚本、浏览器检查、候选管理与剪辑 | MCP 是工具接入方式；Skill 是操作说明。安装插件不能证明已完成集成 |
| 哪些结果需要人决定 | 剧情、人物动机、艺术判断、选片由人参与 | 尚未完成的 Higgsfield 生视频流程不能作为已交付案例 |
| 付费任务异常后怎样恢复 | 视频工作流保留候选与任务 ID；提交不确定时不自动重提 | 接口恢复逻辑经过本地模拟测试，未进行线上 Seedance 调用 |
| 如何验证完成 | 原型状态检查、浏览器加载、路径与资源校验、人工检查图像 | 代码和流程测试不等于真实模型质量测试；机械手检查以人工为主 |
| 失败能否被复用为规则 | 出镜人物范围约束、反馈执行对照、文件夹整理验收 | 这是从具体失败中整理约束；还需要对新任务的效果做检验 |

### 约 60 秒的开场

> 我有一个持续使用 Coding Agent 的创作项目，需要把研究、剧本、交互原型、分镜和视频制作衔接起来。开始主要靠对话推进，后来发现长历史会带入错误的人物设定，交付物也可能通过技术检查却偏离我的真实需求。我开始把人物设定、每镜出镜范围、版本状态和验收条件写清楚，并让程序处理适合确定执行的步骤。视频工具还保存候选、选择和任务状态，遇到提交结果不确定时保留恢复入口。这些让我对上下文、工具执行和验收有了一手体会。实现主要由 AI 辅助完成，我的工作是提出问题、做取舍和验收；目前仍是个人工作流，还没有大规模使用和线上效果数据。

## 五、面试时要讲清楚的几个区别

- **脚本式 Demo 与模型 Agent：**轮椅 Demo 是程序状态机；Bodystorming 原型有模型调用接口、检索、校验与人工选择，但主要路径仍由程序预先规定。
- **Workflow 与自主 Agent：**预定义步骤编排与模型自行决定过程存在差别。面试时先指出项目实际采用哪一种，再解释为什么。[Anthropic 的区分](https://www.anthropic.com/engineering/building-effective-agents)
- **持久化状态与训练：**写入选择、记住规则、恢复进度，均不等于修改模型参数。
- **模拟验证与真实验证：**Bodystorming 有本地模型替身和演示模式；真实服务商质量尚未验证。视频工作流已验证现有素材导入与本地剪辑，线上生成部分只做过模拟测试。
- **艺术质量与工程可用：**文件可打开、接口返回成功、视频能播放，分别只证明对应环节可用。
- **人和 AI 的贡献：**选题来自你的既有项目；人物、方向、问题发现与取舍有你的持续参与；代码和大部分制作由 AI 辅助。具体到每个功能说明分工。

## 六、最值得补的一个实验

先选一个小任务，例如“从确认过的单场剧本整理成可生成的逐镜材料”，比较现有自由对话做法与明确状态／约束／验收的做法。

1. 固定同一份任务输入与模型配置，预先写好可复核的验收条件。
2. 记录完成耗时、人工纠正次数、遗漏或矛盾数量、最终是否通过验收。
3. 保留失败、中断和未完成样本；质量类结果由人按同一标准检查。
4. 记录真实调用费用；没有费用数据时不要用任务秒数冒充人民币成本。
5. 样本量小就按案例实验报告，不把一次比较称作统计有效的 A/B 实验。

如果做用户验证，可以请几位真实会制作此类作品的人尝试相同任务，观察卡点和改稿负担。若要谈轮椅用户需求，还需要另外接触相应真实人群，不能用创作者测试替代。

**当前最需要补的是可复核的使用效果，而非继续增加插件数量。**
